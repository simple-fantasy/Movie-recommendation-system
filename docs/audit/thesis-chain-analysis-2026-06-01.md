## 一、研究问题链

### 1.1 问题的提出（第1章）

研究问题不是一句话抛出来的，而是从三个具体困难逐层推到三个具体问题。

**困难层（1.1.1 研究背景，P27-P30）**：

论文从 MovieLens 32M 的数据特征出发，识别出三个相互叠加的困难：

| 困难 | 来源 | 后果 |
|---|---|---|
| 评分稀疏（0.14%） | 3200万评分 / (27万×8.7万) | 训练信号稀薄，模型易滑向热门推荐 |
| 用户偏好漂移 | 近几周行为权重 > 远期记录 | 简单平均池化失效，需区分有效/过期信号 |
| 可解释性缺失 | 用户需要知道"为什么推这部" | 不是所有算法都能提供推荐理由 |

这三个困难不是并列关系——P29 明确指出"稀疏性和偏好漂移叠加之后，模型很容易滑向一个最省力的解：只推热门电影"。**困难的叠加效应**构成了问题的核心。

**问题层（1.3.1 研究内容，P56）**：

1.2 的文献综述得出一个基本判断后，P56 将困难转化为三个可验证的研究问题：

> 传统协同过滤和深度学习在相同数据集上的真实差距有多大？
> ItemCF 召回 + NCF 重排级联后提升多少、瓶颈在哪？
> 引入 EASE 和 LightGCN 作为不同范式的外部参照后，各方法的相对排序如何变化？

**问题链的特征**：
- Q1 是基准对比问题（传统 vs 深度）
- Q2 是架构验证问题（级联是否有效）
- Q3 是范式校准问题（不同方法论路线的相对位次）
- 三个问题共享同一个评估框架（三层时间切分 + C_all + 全量排序），保证了答案的可比性

### 1.2 问题的锚定（第2章）

第2章不为回答问题，而是为后续章节提供**术语和原理层面的锚点**。每条原理叙述都指向一个具体的设计选择：

| 第2章原理 | 指向的设计选择 | 在何处兑现 |
|---|---|---|
| 调整余弦相似度 → 消除评分尺度偏差 | ItemCF 相似度计算前做用户均值归一化 | 5.2.1 |
| TopK 截断 O(N²)→O(NK) | K=50，435万行 | 5.2.1 |
| 内积的维度独立限制 → MLP 的全连接解除限制 | 选用 MLP-only 架构 | 5.3.1 |
| 三种融合方式（加权/特征/级联） | 选择级联，承认其上限由召回决定 | 2.4 + 5.4.1 |
| BCE vs BPR vs listwise 损失 | 选用 BCE，承认训练-评估目标 gap | 2.3.1 + 5.3.2 |

### 1.3 问题的回答（第6章）

三个问题在第6章得到逐项回答：

**Q1 的回答（6.3.1 + 6.3.4）**：
> ItemCF NDCG@10=0.0490 > EASE 0.0449 > Hybrid 0.0421 > NCF 0.0409 > LightGCN 0.0338
> 差值通过 Wilcoxon 显著性检验（p<0.01），但 Cohen's d 0.03-0.12，差距不大

P466 对结论做了边界限定：
> 不能从这个实验结果推出"深度学习在推荐上不如协同过滤"这样的结论，只能说"在这个数据条件、这个评估协议下，精心调过的 ItemCF 比当前配置的 NCF 和 LightGCN 更好"。

**Q2 的回答（6.3.1 + 6.4.3）**：
> Hybrid R@10=0.0689 > NCF 0.0664（+3.9%），但 Hybrid NDCG@10=0.0421 < ItemCF 0.0490
> 级联有正向增益但受限于召回质量
> 消融实验：recall_k=50 时 Hybrid NDCG=0.05096 反超 ItemCF 0.04833（+5.4%）

**Q3 的回答（6.3.1 + 6.3.2）**：
> EASE Coverage=0.658（ItemCF 的 6.4 倍），排序精度仅微低于 ItemCF
> EASE 代表解析解方法 → 覆盖率优势来自稠密建模 + 不截断
> LightGCN 代表图方法 → 在此稀疏度下排序和覆盖均落后

### 1.4 问题链的闭环（第8章）

第8章将三个回答压缩为三条结论（P582），然后从结论中逆向识别实验的三个盲区（P583）：
- NCF 超参调优不充分（CPU 限制）
- 离线指标 ≠ 用户满意度
- MovieLens 32M 数据时效性（止于 2018 年）

8.2 展望（P585-589）不是泛泛的"未来工作"，而是从实验数据中直接推出的五个具体改进方向，每个都指向论文中已发现的缺口。

**问题链评估**：完整。从困难 → 问题 → 锚定 → 回答 → 边界限定 → 缺口识别，没有跳步，没有"提出但未回答"的问题。

### 3.2 关键设计决策及其理由

| 决策点 | 选择 | 理由 | 代价 |
|---|---|---|---|
| 召回模型 | ItemCF（非 UserCF） | 物品数相对稳定，相似度矩阵可离线缓存；推荐结果可追溯 | 线性相似度，无法捕捉跨维度交互 |
| 重排模型 | NCF MLP-only（非 NeuMF） | CPU 可训练，避免 NeuMF 分阶段预训练的复杂度 | 可能损失 NeuMF 在稠密数据集上的精度增益 |
| 融合方式 | 级联（非加权/特征） | 两模型独立训练互不干扰；工程实现最简单 | 上限由召回阶段决定，NCF 看不到未召回的电影 |
| 损失函数 | BCE + 负采样（非 BPR） | 训练稳定，CPU 上可跑 | 训练目标与 NDCG 评估目标不对齐（0.81 vs 0.041） |
| 评估协议 | 三层时间切分 + 统一 C_all | 消除时间泄漏 + 消除"候选集不同"的混淆变量 | 损失部分测试用户（过滤掉测试样本不全在 C_all 内的用户） |
| 存储策略 | TopK=50 截断 | O(N²)→O(NK)，MySQL 单表可扛 | 矩阵不可逆，被丢弃的相似边不可恢复 |
| NCF 部署 | 异步加载 + 三级回退 | 启动不阻塞；PyTorch 缺失/模型损坏/超时均不导致 500 | 回退到 Popular 时推荐质量等同于非个性化 |
| 前端架构 | Jinja2 SSR + Vue.js 3 CSR 混合 | 首屏快（SSR），交互不刷页面（CSR） | 两套渲染逻辑共存，调试模板变量名拼写错误时不报错 |
| 缓存 | FileSystemCache / SimpleCache | 单机够用，不引入 Redis 依赖 | 重启清空，无法跨进程共享 |

### 3.3 技术路线的关键转折点

论文中有一个值得注意的技术路线转折——**默认配置不是最优配置**。

第5章实现中，Hybrid 的默认参数是 `per_seed_limit=50`、`recall_k=200`。第6章的消融实验发现这两个默认值均非最优：
- `per_seed_limit=10` 时 NDCG 比默认值 50 高出 9.9%
- `recall_k=50` 时 Hybrid NDCG 反超纯 ItemCF 5.4%，而默认值 200 时 Hybrid 低于 ItemCF

这个转折的意义在于：**论文不回避"一开始选错了"**。实现章如实记录了默认配置，实验章如实展示了更优配置。这种"实现→实验→修正"的诚实路径，比"一开始就选对"的完美叙事更有工程可信度。

### 3.4 技术路线的未闭合环节

| 环节 | 状态 | 在第8章的对应改进方向 |
|---|---|---|
| NCF 排序质量 | BCE 损失训练，NDCG 评估——目标不对齐 | 8.2(1)：换 BPR/列表损失 |
| 冷启动 | 当前仅 Popular 兜底 | 8.2(2)：内容特征通道 + 注册偏好热启动 |

**技术路线链评估**：数据→训练→推理→评估→反馈的全链路完整，每个关键决策都给出了理由和代价。已知缺口在被诚实标记在第8章，不伪装成已完成。
